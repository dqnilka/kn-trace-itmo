## 1. Что оцениваем

Три пользовательских эндпоинта формируют итоговый опыт студента:

| Эндпоинт | Выход | Что видит студент |
|----------|-------|-------------------|
| `POST /explain` | `ExplainResponse.explanation_md` | Markdown-объяснение ошибки |
| `POST /recommend` | `RecommendResponse.items[]` | Топ-5 рекомендованных задач с reason |
| `GET /mastery/{user_id}` | `MasteryResponse` | Текущий уровень знаний по темам/концептам |
| `GET /theme/{code}` | `ThemeArticleResponse.summary_md` | Сводка темы |

## 2. Объяснение ошибки (RAG / Bank Explain)

Это **главный пользовательский output** системы. Студент видит его после каждого неверного ответа.

### 2.1. Что оцениваем

Сгенерированный `explanation_md` (до 1200 токенов), структура:
1. Что проверял вопрос
2. Ключевые понятия
3. Подробное объяснение / Разбор вариантов
4. На что обратить внимание / Что повторить

### 2.2. Метрики

#### 2.2.1. Faithfulness (достоверность)

> Насколько объяснение опирается на предоставленный контекст, а не галлюцинирует.

**Как измерять:**

| Подход | Метод | Инструмент |
|--------|-------|------------|
| **Автоматический** | LLM-as-judge: разбить explanation на утверждения, проверить каждое на наличие в `sources[]` | GPT-4o-mini с промптом-чекером |
| **Полуавтоматический** | NLI-based: entailment между source → claim | `deberta-v3-large-mnli` или аналог |
| **Ручной** | Эксперт ставит 0/1: каждое утверждение из объяснения подтверждается источником | Выборка 50–100 объяснений |

**Метрика:** `faithfulness = #supported_claims / #total_claims`

**Интерпретация:**
- `≥ 0.9` — отлично, объяснения хорошо grounded
- `0.7–0.9` — допустимо, есть редкие галлюцинации
- `< 0.7` — проблема, модель придумывает факты

#### 2.2.2. Answer Relevancy (релевантность ответа)

> Насколько объяснение отвечает на вопрос «почему ответ студента неверен».

**Как измерять:**

| Подход | Метод |
|--------|-------|
| **LLM-as-judge** | GPT-4o-mini оценивает по 5-балльной шкале: (1) объясняет ли правильный ответ, (2) объясняет ли почему выбранный вариант неверен, (3) релевантно ли вопросу |
| **Embedding similarity** | `cosine(question + correct_answer, explanation)` — baseline, не заменяет LLM-judge |

**Промпт для LLM-judge:**

```
Оцени объяснение ошибки студента по 5-балльной шкале.

Вопрос: {question}
Правильный ответ: {correct_answer}
Ответ студента: {picked_answer}
Объяснение: {explanation_md}

Критерии:
5 — Объясняет правильный ответ И почему вариант студента неверен И даёт советы
4 — Объясняет правильный ответ и почему вариант студента неверен
3 — Объясняет правильный ответ, но не разбирает ошибку студента
2 — Частично релевантно, но упускает суть
1 — Не релевантно вопросу

Ответь только числом от 1 до 5.
```

**Интерпретация:**
- Средний балл `≥ 4.0` — хорошо
- `3.0–4.0` — приемлемо, требует улучшения промптов
- `< 3.0` — серьёзная проблема с retrieval или generation

#### 2.2.3. Context Precision (точность контекста)

> Насколько релевантные документы были извлечены из ChromaDB.

**Как измерять:**

- Для каждой объяснённой задачи эксперт размечает: какие из `sources[]` действительно полезны (binary relevance).
- `context_precision = mean(precision@k)` по всем запросам, где k — количество возвращённых источников.

**Упрощённая альтернатива (без экспертов):** LLM-as-judge оценивает каждый source как relevant / irrelevant для данного вопроса.

**Интерпретация:**
- `≥ 0.8` — retrieval работает хорошо
- `0.5–0.8` — много шума, возможно нужно поднять пороги cosine или улучшить query
- `< 0.5` — серьезная проблема с embedding или чанкингом

#### 2.2.4. Структурная корректность

> Соблюдена ли требуемая структура Markdown (4 секции).

**Как измерять:** Простой парсер проверяет наличие всех 4 секций:
1. `**Что проверял вопрос**` или `**Что проверял**`
2. `**Ключевые понятия**`
3. `**Подробное объяснение**` или `**Разбор вариантов**`
4. `**На что обратить внимание**` или `**Что повторить**`

**Метрика:** `structure_compliance = #explanations_with_all_sections / #total_explanations`

**Интерпретация:**
- `≥ 0.95` — отлично
- `< 0.90` — промпт нужно ужесточить или добавить Few-shot примеры

## 3. Рекомендатель задач

### 3.1. Что оцениваем

Объект `RecommendResponse` с `items[]` (top-5 задач), где каждая содержит:
- `task_id`, `score`, `expected_p_correct`, `reason`, `target_concepts`, `due_score`

### 3.2. Метрики

#### 3.2.1. Calibration (калибровка предсказаний)

> Насколько `expected_p_correct` совпадает с реальной вероятностью правильного ответа.

**Как измерять:**

1. Собрать исторические события из `events.jsonl`.
2. Для каждого события: найти рекомендацию, предшествующую этому ответу → взять `expected_p_correct`.
3. Сгруппировать ответы по бакетам `[0.0–0.1, 0.1–0.2, ..., 0.9–1.0]`.
4. В каждом бакете: `actual_rate = #correct / #total`.
5. Построить **калибровочную кривую** (reliability diagram).

**Метрики:**
- **ECE (Expected Calibration Error):** `Σ |predicted - actual| × n_bucket / n_total`
- **Brier Score:** `Σ (predicted - actual)² / n_total`

**Интерпретация:**
- ECE `< 0.05` — отличная калибровка
- ECE `0.05–0.10` — допустимо
- ECE `> 0.10` — BKT-параметры нужно калибровать

#### 3.2.2. Ranking Quality (качество ранжирования)

> Насколько рекомендации соответствуют тому, что действительно помогло студенту.

**Как измерять (offline на исторических данных):**

Подход **leave-one-out**:
1. Для каждого студента: взять последнее событие как тестовое.
2. На всех предыдущих — обучить/обновить BKT.
3. Сгенерировать top-5 рекомендаций.
4. Проверить: решена ли рекомендованная задача в будущем? Появился ли learning gain?

**Метрики:**
- **Hit Rate@5:** доля случаев, когда рекомендованная задача была фактически решена следующей
- **NDCG@5:** учитывает позицию релевантной задачи в топе
- **Learning Gain:** `Δ mastery_after_recommended_task` vs `Δ mastery_after_random_task`

**Интерпретация:**
- Hit Rate@5 `≥ 0.3` — рекомендации релевантны (baseline: ~0.05 при 100+ задач)
- NDCG@5 `≥ 0.4` — хорошее ранжирование
- Learning Gain положительный — рекомендации помогают учиться

#### 3.2.3. Diversity (разнообразие)

> Рекомендует ли система разные темы или зацикливается на одной.

**Метрика:** `topic_coverage = #unique_themes_in_recommendations / #total_available_themes`

**Интерпретация:**
- `≥ 0.6` — хорошее покрытие
- `< 0.3` — рекомендатель застревает, проверить cooldown и фильтры

## 4. Отслеживание мастерства (BKT + FSRS)

### 4.1. Что оцениваем

`MasteryResponse`: `overall`, `by_theme`, `by_chapter`, `by_concept`, `due_concepts[]`

### 4.2. Метрики

#### 4.2.1. Предсказательная способность BKT

> Насколько P(L) предсказывает реальный успех студента.

**Как измерять:**

1. Из `events.jsonl` собрать последовательности ответов по каждому концепту.
2. Для каждого ответа: взять P(L) перед ответом.
3. Проверить: `P(correct) = P(L)·(1-P(S)) + (1-P(L))·P(G)` vs actual `is_correct`.

**Метрики:**
- **AUC-ROC:** способность отличить correct от incorrect по P(L)
- **Log-Loss:** `Σ [-y·log(p) - (1-y)·log(1-p)] / n`
- **RMSE:** `√(Σ(p - y)² / n)`

**Интерпретация:**
- AUC `≥ 0.75` — BKT информативен
- AUC `0.60–0.75` — слабый, параметры не калиброваны
- AUC `< 0.60` — эквивалентно случайному угадыванию, нужны другие параметры или модель

#### 4.2.2. Калибровка FSRS (Retrievability)

> Насколько `retrievability = exp(-Δt / stability)` предсказывает забывание.

**Как измерять:**

1. Найти пары событий по одному концепту с временным зазором.
2. `R_predicted = exp(-(t2 - t1) / stability)` → сравнить с `actual = is_correct`.

**Метрика:** Та же калибровочная кривая, ECE.

**Интерпретация:**
- Если R > 0.85, но actual_rate < 0.7 → stability завышена, нужно уменьшить множители FSRS
- Если R < 0.5, но actual_rate > 0.7 → stability занижена

#### 4.2.3. Монотонность мастерства

> Растёт ли P(L) в среднем при правильных ответах и падает при ошибках.

**Как измерять:**
- По всем событиям: `P(L_after) - P(L_before)` → среднее для correct и incorrect.

**Интерпретация:**
- correct: средний ΔP(L) > 0 (ожидается ~+0.05 до +0.15)
- incorrect: средний ΔP(L) < 0 (ожидается ~-0.02 до -0.10)
- Если тренд нарушен — проблема с BKT-формулой или параметрами

## 5. Сводка темы (Theme Summary)

### 5.1. Что оцениваем

`ThemeArticleResponse.summary_md` (~200–300 слов, Markdown).

### 5.2. Метрики

#### 5.2.1. Faithfulness

> Те же методы, что и для объяснений: LLM-as-judge или NLI.

**Интерпретация:** `faithfulness ≥ 0.85` — сводки не галлюцинируют.

#### 5.2.2. Coverage (полнота)

> Все ли ключевые концепты темы упомянуты в сводке.

**Как измерять:**
- Взять список `concepts[]` из `ThemeArticleResponse`.
- Проверить: упомянут ли каждый concept.term в summary_md.
- `coverage = #mentioned_concepts / #total_concepts_in_theme`

**Интерпретация:**
- `≥ 0.7` — сводка покрывает большую часть темы
- `< 0.5` — промпт нужно дополнить требованием упомянуть все ключевые термины

#### 5.2.3. Длина и формат

- Целевой диапазон: 200–300 слов, без заголовков `##`, только bold + lists + paragraphs.
- `format_compliance` — доля сводок, прошедших парсер.

## 7. Практический план внедрения

### Этап 1: Автоматические тесты (без данных, без экспертов)

Что можно сделать **прямо сейчас** на существующих тестах:

| Что | Как | Сложность |
|-----|-----|-----------|
| Structure compliance объяснений | Парсер Markdown на 4 секции | Низкая |
| Format compliance сводок | Проверка длины, отсутствие `##` | Низкая |
| BKT monotonicity unit-test | Параметрический тест: correct→P↑, incorrect→P↓ | Низкая |
| FSRS monotonicity unit-test | correct→S↑, incorrect→S↓ | Низкая |
| Recommender filter consistency | coherence: cooldown не нарушен, mastered не рекомендуются | Средняя |

### Этап 2: LLM-as-judge pipeline

Создать скрипт, который:
1. Выбирает N задач (например, 50).
2. Генерирует объяснения через `POST /explain`.
3. Отправляет explanation + sources в LLM-judge (GPT-4o-mini).
4. Собирает faithfulness и answer relevancy.

**Артефакт:** JSONL-файл с результатами оценки, скрипт для агрегации.

### Этап 3: Оценка на исторических данных

Когда накопится ~500+ событий в `events.jsonl`:

1. **BKT предсказательная способность:** AUC, log-loss.
2. **Калибровка рекомендателя:** ECE, Brier Score.
3. **Ranking quality:** Hit Rate@5, NDCG@5 (leave-one-out).

### Этап 4: Экспертная оценка (по необходимости)

- Разметить 50–100 task→concept связей (precision/recall связывания).
- Разметить 30–50 объяснений (faithfulness + relevancy).
- Сравнить с автоматическими метриками для калибровки LLM-judge.

## Приложение: Интерпретация проблем и действия

| Симптом | Вероятная причина | Действие |
|---------|-------------------|----------|
| Faithfulness < 0.7 | LLM галлюцинирует | Усилить промпт («используй ТОЛЬКО контекст»), добавить few-shot |
| Answer Relevancy < 3.0 | Retriever нерелевантен | Поднять порог cosine (0.35→0.45), проверить эмбеддинги |
| Context Precision < 0.5 | Плохой retrieval | Проверить качество чанкинга, попробовать другой top-k |
| Structure < 0.9 | LLM игнорирует формат | Добавить строгий system prompt с примером |
| ECE > 0.10 | BKT параметры не калиброваны | Fit BKT на исторических данных (EM-алгоритм) |
| AUC < 0.6 | BKT не работает | Попробовать IRT или другую модель |
| Hit Rate@5 < 0.1 | Рекомендации не релевантны | Пересмотреть веса скоринга, ослабить фильтры |
| Coverage < 0.3 | Застревание на одной теме | Увеличить cooldown, добавить diversity bonus |
